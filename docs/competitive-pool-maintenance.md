# 競技池維護與資料庫遷移

本文件整理競技池後台規則與既有資料庫的遷移注意事項。網站功能與本機執行方式見 [README](../README.md)。

## 後台管理

管理員通過站務登入後，使用 `admin.html` 管理競技池期間與名單。一般訪客可直接查看兩服的當期資料，無須登入。

- 台服與陸服各自維護期間與名單，建立期間後固定伺服器歸屬。
- 同服期間不可重疊，前一期結束時間可等於下一期開始時間；不同服可同時進行。
- 期間統一以 UTC+8 輸入與顯示，預覽與 CSV 匯出皆標示伺服器。
- 單隻加入支援 ID、繁簡名稱與部分名稱搜尋；名稱搜尋須選定候選精靈後再加入，批次匯入使用 ID。
- 管理員另可設定台服最新精靈、皮膚與刻印進度。

## 賽季與期數

資料以 `competitive_seasons` 與 `competitive_pools.season_id / pool_number` 管理。後台填寫賽季名稱和數字期數後，自動產生「帝皇賽季 第一池」等標題；未填「賽季」字樣時自動補上。

同服同名賽季會自動沿用，不需另建或選擇；同一賽季的期數不可重複，兩服的賽季彼此獨立。修改某個期間的賽季名稱，只會將該期間改歸新名稱的賽季，不會改名其他期間。

新增與編輯使用 `save_competitive_pool_period` RPC，在同一交易內建立或沿用賽季並儲存期間，失敗時不留下新賽季。

## 套用 SQL 前

`sql/` 包含現有功能的建置與遷移腳本，不是完整的新環境初始化方案。新環境需先建立管理員判定與相關權限依賴，並確認資料表、RPC 及 RLS 規則符合部署需求。

競技池名單使用 `sql/competitive_pools.sql` 建立基本結構，伺服器與賽季功能再分別透過下列遷移加入。請先核對資料庫目前的結構及資料，再決定需執行的步驟。

以下檢查及遷移需另行在 Supabase SQL Editor 執行；修改前端檔案或部署靜態網站不會自動套用 SQL。

## 伺服器遷移

1. 執行 [唯讀檢查](../sql/inspect_competitive_pool_servers.sql)，確認同服期間沒有重疊。
2. 先修正檢查發現的期間衝突，再執行 [伺服器遷移](../sql/competitive_pool_servers.sql)。
3. 發布支援服別的前後台程式。

遷移會將既有未標記期間歸入台服，保留期間 ID 與精靈名單，不會將資料複製至陸服。若既有期間重疊，整筆遷移交易會回滾，需先人工核對及修正日期。

兩服皆為公開資料，沿用當期公開讀取與管理員寫入的 RLS，不以服別限制閱讀權限。

## 賽季遷移

1. 確認伺服器遷移已完成。
2. 執行 [唯讀檢查](../sql/inspect_competitive_pool_seasons.sql)，核對舊標題拆分出的賽季與期數。
3. 處理無法辨識的標題或重複期數後，執行 [賽季遷移](../sql/competitive_pool_seasons.sql)。
4. 發布相符的前後台版本。

遷移保留期間 ID、時間與精靈名單，將舊標題拆為賽季及期數。無法辨識的標題或重複期數會使整筆交易回滾。原 `name` 欄位留存作為遷移前標題的核對資料，新功能不再讀寫該欄位。

**套用賽季遷移後，舊版後台無法建立期間，必須搭配新版程式發布。**

## 陸服票選服務

競技池名單由 Supabase 提供；陸服票選排名另由 Bot 共用服務的 `GET /api/cn/votes` 提供，端點設於 `js/competitive/votes-api.js`。

- 一般時段共用後端 5 分鐘快取；每週三台灣時間 23:45～23:59 每次查詢重新取得票數，以 API 回傳狀態為準。
- 前端僅提供手動更新，不自動輪詢；更新失敗會保留並標示上次成功取得的資料。
- 切回台服或名單會取消前端請求，過期回應不會覆蓋目前頁面。
- 直接連結 `?tab=competitive&server=cn&poolview=votes` 可開啟投票數據；一般功能入口與伺服器切換預設顯示名單。

玩家查詢及陸服票選共用網站的繁簡名稱轉換政策，維護位置為 `js/shared/chinese.js`。名稱中的岳、杰、托、里、背等用字保留，啓統一轉為啟。
